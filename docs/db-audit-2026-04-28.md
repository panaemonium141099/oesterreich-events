## Befund 1 — Realtime WAL ist 85.8% der DB-Zeit

```
total_ms     pct    calls    mean_ms  query
9,318,992   45.8%   946,041  9.9    realtime.list_changes (typ A)
8,141,926   40.0%   761,614 10.7    realtime.list_changes (typ B)
```

**Was passiert:** Jeder eingeloggte Browser-Tab subscribed sich auf 3-4
gleiche Tabellen, ohne Server-side `filter`. Pro WAL-Event muss
realtime.list_changes JSON aus `wal->>` extrahieren und alle subscribed
clients beliefern. Das schiere Volumen (1.7 Mio Calls) sagt: das passiert
bei jedem winzigen DB-Change, multipliziert mit Zahl der subscribed clients.

**Aktuell subscribed (publication `supabase_realtime`):**

```
activity_comments, activity_likes, direct_messages, friendships,
group_messages, group_pinboard_notes, notifications
```

**Code-Subscription-Inventar** (Subagent-Scan, alle bestätigt):

| File:Line | Channel | Tabelle | Filter |
|---|---|---|---|
| `src/components/Notifications/NotificationToast.tsx:60` | `notification-toast` | `notifications` | `user_id=eq.${user.id}` ✅ |
| `src/components/Notifications/NotificationBell.tsx:41` | `notification-bell` | `notifications` | `user_id=eq.${user.id}` ✅ |
| `src/app/notifications/NotificationsPageClient.tsx:112` | `notifications-page` | `notifications` | `user_id=eq.${user.id}` ✅ |
| `src/components/Layout/SocialNav.tsx:102` | `social-nav-unread` | `direct_messages` | `receiver_id=eq.${user.id}` ✅ |
| `src/app/messages/MessagesPageClient.tsx:161` | `dm-list` | `direct_messages` | **kein Filter** ❌ |
| `src/app/messages/[userId]/MessageThreadPageClient.tsx:139` | `dm-${a-b}` | `direct_messages` | per-pair filter ✅ |
| `src/app/groups/[id]/GroupDetailPageClient.tsx:293` | `group-dash-${id}` | `group_messages` | `group_id=eq.${id}` ✅ |
| `src/components/Planer/detail/Pinboard.tsx:133` | `pinboard:${id}` | `group_pinboard_notes` | `group_id=eq.${id}` ✅ |

**Probleme:**

- **3 Channels für `notifications` pro User** — alle korrekt gefiltert, aber
  3× WAL-Lookup pro Event (jede Subscription = ein Eintrag in
  `subscription_ids` Aggregation). Konsolidiere zu einem channel pro user
  und multiplexe in React Context.
- **`MessagesPageClient.tsx:161` hat keinen Filter** — die Subscription kommt
  ohne `filter:` Argument, was bedeutet **jede DM-Änderung in der ganzen DB
  wird an diesen Client gestreamt**. RLS verhindert dass die *Daten* gelesen
  werden, aber die WAL-Decode-Arbeit fällt trotzdem an. Im JS muss dann
  pro Event geprüft werden ob es relevant ist. Bei wachsender User-Base
  skaliert das schlecht.

**Fix-Migration & Code:**

```typescript
// src/components/Notifications/NotificationsProvider.tsx (NEU, Root-Layout)
'use client';
const NotificationsCtx = createContext<{rows: Notification[]; markRead: (id:string)=>void}>(...);

export function NotificationsProvider({children, userId}) {
  const [rows, setRows] = useState<Notification[]>([]);
  useEffect(() => {
    if (!userId) return;
    const ch = supabase.channel(`notifications:${userId}`)
      .on('postgres_changes', {
        event: '*', schema: 'public', table: 'notifications',
        filter: `user_id=eq.${userId}`,
      }, (payload) => setRows(prev => mergeNotification(prev, payload)))
      .subscribe();
    return () => { supabase.removeChannel(ch); };
  }, [userId]);
  return <NotificationsCtx value={{rows, markRead}}>{children}</NotificationsCtx>;
}

// In NotificationBell, NotificationToast, NotificationsPageClient:
// Statt eigenem channel:  const {rows} = useContext(NotificationsCtx);
```

CREATE OR REPLACE FUNCTION public.bulk_update_event_geocoding(p_updates jsonb)
RETURNS integer LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
DECLARE affected int;
BEGIN
  WITH src AS (
    SELECT (e->>'id')::uuid AS id,
           (e->>'latitude')::double precision AS latitude,
           (e->>'longitude')::double precision AS longitude,
           (e->>'geocoding_confidence')::double precision AS geocoding_confidence,
           (e->>'geocoding_source')::text AS geocoding_source
    FROM jsonb_array_elements(p_updates) AS e
  )
  UPDATE events e
     SET latitude = src.latitude,
         longitude = src.longitude,
         geocoding_confidence = src.geocoding_confidence,
         geocoding_source = src.geocoding_source
    FROM src
   WHERE e.id = src.id;
  GET DIAGNOSTICS affected = ROW_COUNT;
  RETURN affected;
END $$;

**Code-Refactor:** Pro Script eine `flushBatch()`-Helper-Funktion die je
~500 Updates sammelt, dann via RPC schickt. Beispiel für openai-geocode.ts:

```typescript
const queue: GeocodingUpdate[] = [];
const FLUSH = 500;
async function queueUpdate(u: GeocodingUpdate) {
  queue.push(u);
  if (queue.length >= FLUSH) await flush();
}
async function flush() {
  if (!queue.length) return;
  const batch = queue.splice(0, queue.length);
  const { error } = await supabase.rpc('bulk_update_event_geocoding', { p_updates: batch });
  if (error) throw error;
}
// Am Ende des Scripts: await flush();
```

**Erwarteter Effekt:** Statt 200ms-Mean × 449k Calls = 25 h für openai-geocode
→ ~500 RPC Calls × 100ms = 50 s. Ähnlich für die anderen Scripts.

## Befund 3 — `visibility = 'public' OR visibility IS NULL` ist toter Code

```
SELECT count(*) FROM events;
→ total: 172,901
→ visibility IS NULL: 0
→ visibility = 'public': 172,901
→ visibility = 'private': 0
→ distinct values: 1
```

Die `OR visibility IS NULL`-Klausel im Filter (taucht in allen Hub-Page-
Queries auf, generiert von PostgREST aus dem Code) macht dass Postgres den
`idx_events_visibility` nicht nutzt — der Planner muss zwischen Index-Scan
und Filter-Scan wählen, weil `OR` über Index-Spalten ohne UNION schlecht
optimierbar ist. EXPLAIN bestätigt: bei deep-offset wird nur
`idx_events_start_date` benutzt, der Rest fällt zurück auf Filter
(Rows Removed by Filter).

Plus: eine Spalte mit nur **einem** distinct value bringt einen Index sowieso
nichts — `idx_events_visibility` (3.5 MB, 22 scans) sollte gedroppt werden.

**Fix:**

```sql
-- 1. NULL-Defense: Spalte als NOT NULL markieren
UPDATE events SET visibility = 'public' WHERE visibility IS NULL;
ALTER TABLE events ALTER COLUMN visibility SET NOT NULL;
ALTER TABLE events ALTER COLUMN visibility SET DEFAULT 'public';

-- 2. Useless index droppen
DROP INDEX IF EXISTS public.idx_events_visibility;
```

**Code-Anpassung:** Alle `or('visibility.eq.public,visibility.is.null')`
und `.eq('visibility', 'public')` in Hub-Pages durch direktes Weglassen
ersetzen — wenn alle Events eh public sind, ist der Filter überflüssig.
Wenn private Events kommen sollen, sollte `visibility = 'public'` aber
EXPLIZIT bleiben (NICHT mehr OR IS NULL).

Am Layer der API-Routen lohnt es einmal global zu suchen:
```bash
grep -rn "visibility.is.null" src/
grep -rn "or('visibility" src/
```

## Befund 5 — `work_mem` zu klein → 20 GB temp_files

```
work_mem               3500 KB   (3.4 MB)
temp_files (lifetime)  3,988 files
temp_bytes (lifetime)  20 GB
```

3.4 MB ist Postgres-Default für allerkleinste Instances. Auf der eu-central-1
Instance (mit ~1 GB RAM für Postgres) sollten 16 MB pro Connection problemlos
gehen. Jeder Sort/HashAggregate über mehr als 3.4 MB spillt **auf Platte** —
die 20 GB sind echt geschriebene Disk-Daten allein für temp.

Die meisten Hub-Page-Queries haben `ORDER BY start_date LIMIT N` und sind
zu klein. Das echte Spillen passiert bei den **paginierten Counts** und
den **Backfill-Reads** mit großen Result Sets.

**Fix (live Setting):**

```sql
-- statement_timeout pattern wiederverwenden
ALTER ROLE anon          SET work_mem = '16MB';
ALTER ROLE authenticated SET work_mem = '16MB';
ALTER ROLE service_role  SET work_mem = '32MB';
```

**Risiko:** Pro Connection × Sort-Operation kann das `work_mem × N` allokieren.
Bei 60 max_connections × 16 MB × 2 sorts/query = bis zu ~2 GB peak. Free-Tier
hat eher knapp Memory. Falls es Probleme gibt, auf 8 MB runter.

## Befund 6 — `count: 'exact'` unnötig auf 35+ Endpunkten

PostgREST mit `Prefer: count=exact` löst eine zweite Query mit identischem
WHERE aus, plain um zu zählen. Auf der `events`-Tabelle (200k Zeilen) ist
das ein voller Index- oder Tabellen-Scan zusätzlich zum Result-Set.

In pg_stat_statements sichtbar als `pgrst_source_count AS (SELECT $7 FROM events WHERE …)`:

```
calls   mean_ms  total_ms   query
6,246    560.8   3,502,785  events.id WHERE start_date >= … AND updated_at > …
                            (== "all newly-updated events count")
```

Das erste oder die zweite Hälfte der mean_ms kommt vom Count.

**Code-Stellen** (vom Subagent gefunden, nicht erschöpfend):

- `src/app/admin/overview/page.tsx` — 5× `count: 'exact'` auf große Tabellen
- `src/app/admin/users/page.tsx` — Profile + Roles count
- `src/app/admin/dedup/stats/route.ts` — multi-table counts
- `src/app/api/admin/quality-flags/route.ts`, `…/review-queue/route.ts`
- `src/app/api/admin/dedup/uncertain/route.ts`
- `src/app/api/venues/[id]/route.ts:45-47` — events-pro-Venue mit exact count

**Empfehlung pro Use-Case:**

| Wo | Aktuell | Empfohlen |
|---|---|---|
| Hub-Page-Anzeige "X Events" | `exact` | `estimated` (PG nutzt pg_class.reltuples + Filter-Selectivity, ist meistens innerhalb 5%) |
| Admin-Dashboard "Total Events" | `exact` | `estimated` — Admin sieht "≈ 198,000" reicht |
| Pagination "Page 5 of 50" | `exact` | `planned` (planner-estimated) ist OK, oder Cursor ohne Pagezahl |
| API-Antworten an externe Konsumenten | `exact` | `exact` lassen wenn Vertrag das verlangt |
| Map-Cluster-Count, Wochenend-Highlights | `exact` | weglassen ganz (kein Count nötig) |

**Code-Pattern (Beispiel):**

```typescript
// alt
.select('id, title, ...', { count: 'exact' })

// neu (für die meisten Hub-Pages)
.select('id, title, ...', { count: 'estimated' })

// oder ganz weglassen, wenn der Count nicht angezeigt wird
.select('id, title, ...')
```

## Befund 9 — Multiple Permissive Policies (echte Duplikate)

Gestern wurden 95 Policies für InitPlan re-created. Dabei kamen 2 echte
Duplikate raus die der Advisor bestätigt:

```
group_pinboard_notes DELETE: pinboard_notes_delete_own + pinboard_notes_delete_owner
                             → konsolidieren zu einer
groups UPDATE:               "Group admins can update" + groups_update_owner_or_admin
                             → konsolidieren zu einer
```

Plus zwei Cosmetic-Duplikate (gleicher Name, einmal anon, einmal authenticated):

```
event_series SELECT: event_series_public_read (×2)
venues SELECT:       venues_public_read (×2)
```

Die Cosmetics sind kein Problem — Postgres dedupliziert intern. Die echten
Doppelten kosten 2× Policy-Auswertung pro Row.

**Fix:**

```sql
-- group_pinboard_notes: own (== created by current user) ist Subset von owner.
-- Sicher gleichzeitig: WHERE user_id = auth.uid() OR <ist Group-Owner>
DROP POLICY IF EXISTS pinboard_notes_delete_own   ON group_pinboard_notes;
DROP POLICY IF EXISTS pinboard_notes_delete_owner ON group_pinboard_notes;
CREATE POLICY pinboard_notes_delete ON group_pinboard_notes FOR DELETE
TO authenticated USING (
  user_id = (SELECT auth.uid())
  OR EXISTS (
    SELECT 1 FROM groups g
    WHERE g.id = group_pinboard_notes.group_id
      AND g.created_by = (SELECT auth.uid())
  )
);

-- groups UPDATE: zwei Logiken — beide Owner sein ODER admin sein
DROP POLICY IF EXISTS "Group admins can update" ON groups;
DROP POLICY IF EXISTS groups_update_owner_or_admin ON groups;
CREATE POLICY groups_update ON groups FOR UPDATE
TO authenticated
USING (
  created_by = (SELECT auth.uid())
  OR EXISTS (
    SELECT 1 FROM group_members gm
    WHERE gm.group_id = groups.id
      AND gm.user_id = (SELECT auth.uid())
      AND gm.role = 'admin'
  )
)
WITH CHECK (
  created_by = (SELECT auth.uid())
  OR EXISTS (
    SELECT 1 FROM group_members gm
    WHERE gm.group_id = groups.id
      AND gm.user_id = (SELECT auth.uid())
      AND gm.role = 'admin'
  )
);
```

**Cave:** Vor Apply die Policy-Body der Originale ansehen und
zusammenmergen. Die obigen sind aus dem Kontext geschätzt.

## Befund 10 — Security-DEFINER Funktionen für `anon` / `authenticated` aufrufbar

Advisor flag: 17 Funktionen executable durch `anon` als SECURITY DEFINER.
Die meisten sind RLS-Helper (`is_god`, `is_group_member`, `user_group_ids`)
die intern im Policy-Body benutzt werden — die brauchen DEFINER damit sie
unter dem definierenden Owner laufen, nicht unter dem aufrufenden User.

**Aber sie sind direkt via REST aufrufbar:**

```
POST /rest/v1/rpc/is_god      → liefert true/false des aufrufenden Users
POST /rest/v1/rpc/user_group_ids → mit beliebiger UUID listet alle Groups eines beliebigen Users
POST /rest/v1/rpc/is_group_member → mit beliebiger UUID-Kombi
```

`user_group_ids(p_user_id uuid)` ist real ein Information-Disclosure-Risiko —
ein eingeloggter User kann irgendeine UUID einsetzen und kriegt die Group-Liste
zurück.

**Fix:**

```sql
REVOKE EXECUTE ON FUNCTION public.user_group_ids(uuid) FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.is_group_member(uuid, uuid) FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.is_group_creator(uuid, uuid) FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.is_god() FROM anon;  -- authenticated darf, ist intended
REVOKE EXECUTE ON FUNCTION public.handle_new_user() FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.handle_new_group() FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.bulk_update_event_scores(jsonb) FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.delete_derived_event(uuid) FROM anon;  -- nur authenticated mit RLS
REVOKE EXECUTE ON FUNCTION public.cleanup_event_reminders() FROM anon, authenticated;
-- match_* und seo_count_* sind read-only — ggf. behalten

-- Falls eines davon explizit von Server-Code aufgerufen wird,
-- nur service_role lassen:
GRANT EXECUTE ON FUNCTION public.bulk_update_event_scores(jsonb) TO service_role;
```

## Anhang: Reproduzier-Queries für Re-Audit

Alle 30+ SQL-Queries dieses Audits sind in der DB-Audit-Session verlaufen.
Die wichtigsten Quick-Checks für die Zukunft:

```sql
-- 1. Top-30 by total exec time
SELECT round(total_exec_time::numeric,0) AS total_ms,
       round((total_exec_time/SUM(total_exec_time) OVER ()*100)::numeric,1) AS pct,
       calls, round(mean_exec_time::numeric,1) AS mean_ms,
       LEFT(regexp_replace(query,'\s+',' ','g'),200) AS sql
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC LIMIT 30;

-- 2. Sequentielle Scan-Hotspots
SELECT relname, n_live_tup, seq_scan, idx_scan,
       round(100.0*seq_scan/NULLIF(seq_scan+idx_scan,0),1) AS pct_seq,
       seq_tup_read
FROM pg_stat_user_tables
WHERE schemaname='public' AND seq_scan > 100
ORDER BY seq_tup_read DESC LIMIT 20;

-- 3. Unused indexes >100KB
SELECT relname AS table, indexrelname AS idx,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size, idx_scan
FROM pg_stat_user_indexes ui
JOIN pg_index pi ON pi.indexrelid = ui.indexrelid
WHERE schemaname='public' AND idx_scan = 0
  AND NOT pi.indisunique AND NOT pi.indisprimary
  AND pg_relation_size(indexrelid) > 100*1024
ORDER BY pg_relation_size(indexrelid) DESC;

-- 4. Reset wenn man frische Stats will (Vorsicht)
-- SELECT pg_stat_statements_reset();
```
