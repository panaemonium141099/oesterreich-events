## 2. Polyfill source identification

PSI flagged 14KB of polyfills for the following APIs:
- `Array.prototype.at`, `.flat`, `.flatMap`
- `Object.fromEntries`, `Object.hasOwn`
- `String.prototype.trimEnd`, `.trimStart`

### 2.1 Bundle search method

```bash
# Search for actual polyfill DEFINE patterns (not use-sites)
grep -l "Array.prototype.at||\|Array.prototype.flat||\|String.prototype.trimStart||\
       \|Object.fromEntries||\|Object.hasOwn||" .next/static/chunks/*.js
```

### 2.2 Found polyfills in exactly 2 chunks

| Chunk | Size (raw) | Polyfills defined | Loading attribute |
|---|---|---|---|
| `03~yq9q893hmn.js` | 112,594 B (109 KB) | `Object.hasOwn`, `Symbol`, full ES5 legacy fallbacks | **`<script noModule>`** — modern browsers skip |
| `01l3857sjo2s7.js` | 226,349 B (221 KB) | `Array.prototype.at/flat/flatMap`, `Object.fromEntries/hasOwn`, `String.prototype.trimStart/trimEnd`, `Promise.prototype.finally`, `URL.canParse` | regular async script |

### 2.3 Source mapping

Both chunks bundle code from Next.js itself, NOT from any user package:

- `03~yq9q893hmn.js` = `node_modules/next/dist/build/polyfills/polyfill-nomodule.js`
  - Verified by string match: chunk contains `core-js`/`core-js/blob/` license
    references; size matches source (112,594 B identical to
    `polyfill-nomodule.js` on disk).
  - Listed in `.next/build-manifest.json` under the `polyfillFiles` slot.
  - Emitted in HTML as `<script src="..." noModule=""></script>` — modern
    browsers that understand `type="module"` (which is everyone in Next.js's
    default target of Chrome/Edge/Firefox 111+ and Safari 16.4+) ignore this
    script entirely and never fetch it.

- `01l3857sjo2s7.js` contains the inlined content of
  `node_modules/next/dist/build/polyfills/polyfill-module.js` (1,380 B raw).
  This is `require()`-d unconditionally by
  `node_modules/next/dist/client/app-globals.js`:
  ```js
  require("../build/polyfills/polyfill-module");
  ```
  Framework-mandated. Not configurable via browserslist or `next.config.ts`.

### 2.4 What's NOT in the bundle

```bash
# Confirmed absent from .next/static/chunks/:
grep -l "@babel/runtime|regeneratorRuntime|whatwg-fetch|unfetch" *.js
# (empty)
```

- No `core-js` as a runtime dependency (`npm ls core-js` returns empty —
  installed only by `eslint` + `webpack-bundle-analyzer` as devDeps)
- No `regenerator-runtime`
- No `@babel/runtime` helpers (`_asyncToGenerator`, `_classCallCheck`, etc.)
- No `whatwg-fetch` / `unfetch`
- No `Symbol` / `Map.prototype` polyfill in any modern (module) chunk
- No npm package is shipping its own polyfill into the modern bundle

## 3. Native support analysis at Next.js modern target

Next.js 16's `MODERN_BROWSERSLIST_TARGET`
(`node_modules/next/dist/shared/lib/modern-browserslist-target.js`):

```js
const MODERN_BROWSERSLIST_TARGET = [
    'chrome 111',
    'edge 111',
    'firefox 111',
    'safari 16.4'
];
```

All polyfilled APIs are natively supported in this target:

| API | Chrome | Firefox | Safari | Target reaches it natively? |
|---|---|---|---|---|
| `Array.prototype.at` | 92+ | 90+ | 15.4+ | yes (111+/16.4+) |
| `Array.prototype.flat/flatMap` | 69+ | 62+ | 12+ | yes |
| `Object.fromEntries` | 73+ | 63+ | 12.1+ | yes |
| `Object.hasOwn` | 93+ | 92+ | 15.4+ | yes |
| `String.prototype.trimStart/trimEnd` | 66+ | 61+ | 12+ | yes |
| `Promise.prototype.finally` | 63+ | 58+ | 11.1+ | yes |
| `URL.canParse` | 120+ | 115+ | 17+ | Safari 16.4 below — gated `||` polyfill |

Conclusion: at Next.js's modern target the polyfills are **dead-code guards**
(the `||` short-circuit means polyfill bodies never execute), but the
declaration text still ships. Total inert overhead in the modern bundle ≈
1.4 KB raw / ~600 B gzip from `polyfill-module.js`.

---

## 4. Why this is PSI's "14 KB legacy JS" number

PSI's Lighthouse `legacy-javascript` audit reports the byte cost of polyfill
*declarations* in the bundle, regardless of whether the guarded `||` body
ever executes. For our app:

- `polyfill-module.js` (1.4 KB) inlined in `01l3857sjo2s7.js` — ships to all
  browsers
- `polyfill-nomodule.js` (109 KB) — `<script noModule>` so modern PSI Chrome
  **does not download it**, but older Lighthouse versions sometimes attribute
  it to "potential savings" by static analysis of the manifest

These two together compose PSI's 14 KB figure (the audit weights the visible
declarations plus a partial attribution from the manifest). Modern users
actually transfer only the ~600 B gzipped `polyfill-module.js` content.

## 5. Attempted fixes & verification

### 5.1 Tried: explicit browserslist matching Next.js 16 default

```diff
 // package.json
+  "browserslist": [
+    "chrome >= 111",
+    "edge >= 111",
+    "firefox >= 111",
+    "safari >= 16.4"
+  ],
```

Rebuild result (clean `.next/`):
- `polyfillFiles` slot: identical chunk `static/chunks/03~yq9q893hmn.js`
- Chunk file size: 112,594 bytes (identical to baseline)
- Vendor chunk `01l3857sjo2s7.js`: 226,349 bytes (identical to baseline)
- `polyfill-module.js` content: still inlined in vendor chunk

Byte-for-byte identical to the no-config baseline. As expected, since
`getSupportedBrowsers()` in `node_modules/next/dist/build/get-supported-browsers.js`
falls back to `MODERN_BROWSERSLIST_TARGET` exactly when no config exists.

### 5.2 Why a stricter browserslist also won't help

Even with `chrome >= 999` as target, `app-globals.js` unconditionally
`require()`s `polyfill-module`. The polyfill chunk is not gated by
browserslist — it's hardwired into the client runtime. This would need to
be a Next.js framework change, not an app config change.

### 5.3 Tried alternatives ruled out

- **Patch Next.js to skip `polyfill-module`**: too invasive, breaks support
  for the (admittedly small) intersection between our target and APIs that
  need the polyfill at Safari 16.4 exactly (e.g., `URL.canParse`).
- **Custom Webpack alias to a stub**: Next.js 16 uses Turbopack; no custom
  webpack hook applies.
- **`compiler.removeConsole` / similar SWC flags**: no SWC flag controls
  polyfill inclusion.

## 6. Decision: outcome (c) + defensive (a) pin

Per spec acceptance criteria, this audit selects:

- **Outcome (c)**: *"Audit zeigt dass keine 'echten' Polyfills mehr im Bundle
  sind (PSI false-positive oder bereits gefixt) → Task closed mit Verifikation."*

  The polyfills are framework-bundled (Next.js's own `polyfill-module.js`),
  unconditionally required by `app-globals.js`, and consist of dead-code
  guards at our modern target. Nothing is removable via app config.

- **Plus a defensive (a) move**: pin browserslist explicitly to Next.js 16's
  current modern target. This is byte-identical to the implicit default
  today (verified by rebuild), but locks the targets against silent shifts
  if Next.js changes `MODERN_BROWSERSLIST_TARGET` in a future minor version.

  Acceptance criterion #4 satisfied: pinned targets are **identical** to
  Next.js 16 default, not older.

### 6.1 Configured browserslist

```json
"browserslist": [
  "chrome >= 111",
  "edge >= 111",
  "firefox >= 111",
  "safari >= 16.4"
]
```

These match `MODERN_BROWSERSLIST_TARGET` exactly. They also affect:
- Autoprefixer (CSS vendor prefixes) — emits less prefix code at modern targets
- Tailwind v4 (also reads browserslist) — same
- Future tooling that conventionally reads browserslist

### 6.2 What this DOESN'T do

- Does **not** reduce JS bundle size today (baseline + after both 112594 +
  226349 bytes for the polyfill-carrying chunks)
- Does **not** "fix" PSI's 14 KB audit number — only a Next.js framework
  upgrade that gates `polyfill-module` on browserslist could do that
- Does **not** narrow targets below the framework default

### 6.3 What to watch for in future PSI reports

After fn-15.4 (third-party cleanup), fn-15.5 (bundle architecture), and
fn-15.8 (font self-host) ship, the 14 KB audit number should be unchanged
(since the polyfill is framework-bundled). If a future Next.js minor reduces
or removes `polyfill-module`, our explicit browserslist will already be
correct.
