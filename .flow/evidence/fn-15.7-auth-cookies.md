## Authoritative cookie name derivation

`@supabase/supabase-js@2.100.1` — `src/SupabaseClient.ts:294`:

```ts
const defaultStorageKey = `sb-${baseUrl.hostname.split('.')[0]}-auth-token`
```

With `baseUrl = new URL('https://booljdtrktpotsenbnut.supabase.co')`:
- `baseUrl.hostname` → `booljdtrktpotsenbnut.supabase.co`
- `split('.')[0]` → `booljdtrktpotsenbnut`
- `defaultStorageKey` → `sb-booljdtrktpotsenbnut-auth-token`

`@supabase/ssr@0.9` uses this `storageKey` directly as the cookie name (no
override in `src/lib/supabase/server.ts` or `src/lib/supabase/client.ts`).

## Chunking behaviour

`@supabase/ssr` `dist/main/utils/chunker.js`:

- `MAX_CHUNK_SIZE = 3180`
- If the JWT-encoded session is >3180 chars (typical for PKCE +
  refresh-token + user metadata + JWKS), the cookie is split into
  `sb-booljdtrktpotsenbnut-auth-token.0`, `.1`, … (regex
  `/^(.*)[.](0|[1-9][0-9]*)$/`).
- An unchunked session ships as a single `sb-booljdtrktpotsenbnut-auth-token`
  cookie.

## Effective production cookie set (logged-in)

| Cookie | When present |
|---|---|
| `sb-booljdtrktpotsenbnut-auth-token` | Small session (no chunking) |
| `sb-booljdtrktpotsenbnut-auth-token.0` | Chunked session, mandatory first chunk |
| `sb-booljdtrktpotsenbnut-auth-token.1` (+) | Chunked session continuation, only if size requires |

The cookie value is base64url-prefixed (`base64-`-prefix) and contains
PKCE + access-token + refresh-token + user-claims serialised as JSON.

## What the middleware matcher should be

A presence-check on `sb-` prefix + `auth-token` substring catches both the
unchunked and the chunked variants, and is forward-compatible with the
project-ref being rotated (only the prefix changes).

The existing helper in `src/middleware.ts` already implements this:

```ts
if (cookie.name.startsWith('sb-') && cookie.name.includes('auth-token')) {
  return true;
}
```

That is the correct, forward-compatible pattern. It does NOT match
`-code-verifier` (PKCE intermediate cookie, value of `sb-...-auth-code-verifier`)
because `auth-code-verifier` doesn't contain `auth-token`. PKCE-only state
(no session yet) therefore correctly bypasses the Edge redirect — anonymous
users see the Landing.

## Stale-cookie / refresh-only edge case

The task spec calls out: "Wenn nur `sb-refresh-token` (also Access expired)
vorhanden ist, KEIN Redirect". In this Supabase setup that case **does not
arise**: refresh-token and access-token share one consolidated cookie. When
the token is refreshed the cookie is re-written as a single unit. The only
way to lose just the access half is to manually delete it client-side — at
which point the consolidated cookie itself is dropped or replaced.

Conclusion: presence of `sb-...-auth-token` ⇒ the browser holds at least
some session material; we redirect to `/feed`. If that session is stale,
`/feed`'s own `getUser()` call invalidates it and bounces back to
`/auth/login`. ISR on `/` stays untouched.

## Done

Cookie names confirmed. Middleware can rely on the
