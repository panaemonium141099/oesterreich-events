## Description
Smart-Suche versteht Aktivitaets-Absichten und liefert sie als separates, additives Feld ueber einen EIGENEN Retrieval-Pfad aus — ohne den Event-Pfad anzufassen. Activity-only-Queries duerfen NIE in den Event-Fallback laufen.

**Size:** M
**Files:** src/lib/search/smart-query.ts, src/app/api/search/semantic/route.ts, supabase/migrations/<ts>_search_activities_rpc.sql, src/components/Entdecken/ (ActivityResultCard + Block in V4EntdeckenSmartMode), src/__tests__/lib/smart-query*.ts + Route-Tests

## Approach
- SearchIntent (smart-query.ts:216-224): contentTypes: ('event'|'activity')[] ergaenzen; validateIntent (:251-283) whitelistet via cleanList-Muster. **Normalisierungs-Regel: ist contentTypes nach Validierung leer (Feld fehlt, leeres Array, nur unbekannte Werte), wird IMMER auf ['event'] normalisiert** — die Pfad-Gating-Logik sieht nie ein leeres Array (kein Drift fuer Bestandsqueries, keine versehentliche Event-Unterdrueckung).
- intentIsEmpty (:286-291) MUSS non-default contentTypes als Signal werten (Epic E9).
- **Pfad-Gating (Epic E9, verbindlich):** enthaelt contentTypes kein 'event' -> Event-Retrieval INKLUSIVE Top-Score-Fallback wird NICHT aufgerufen, Response liefert matches=[]. Enthaelt contentTypes kein 'activity' -> kein Activity-Pfad (Default-Verhalten identisch zu heute).
- Gemini: responseSchema (route.ts:96-107) + Prompt-Regel fuer Aktivitaets-Absichten ("wo kann ich mountaincart fahren", "was tun bei Regen in X").
- **Deterministischer No-AI-Fallback (Pflicht):** die Route degradiert heute bewusst, wenn Gemini fehlt/timeoutet — dafuer braucht es einen regex-/keyword-basierten Aktivitaets-Klassifikator VOR dem Pfad-Gating (Keywords aus der Task-1-Topic-Whitelist: mountaincart, rodel, klettersteig, hochseilgarten, freibad, "was tun", ...), der contentTypes auch ohne LLM setzt. Sonst laufen Activity-Queries im Fallback-Modus doch in den Event-Pfad.
- Eigener Retrieval-Pfad `fetchActivityMatches(intent)` NEBEN fetchCandidates (route.ts:195-275): **die trgm-Suche laeuft ueber eine SQL-RPC** `search_activities(q, tags, setting, bundesland, lat, lng, radius_km, max_results)` — `setting` wird als SQL-Filter VOR Ranking und Result-Cap angewandt (sonst verdraengen besser gerankte Outdoor-Treffer die Indoor-Matches aus der Shortlist) (eigene Migration in diesem Task; PostgREST kann kein indexgestuetztes `%`/similarity-Ranking) — **trgm NUR auf name** (GIN gin_trgm_ops aus Task 1) + Tag-Filter; description fliesst nur als Sekundaer-Scoring ueber die bereits geladene Shortlist ein (kein description-Index). Route ruft supabase.rpc('search_activities', ...). **Fallback-Zweig ohne Suchterme (Pflicht):** bleibt nach Location-/Stopword-Stripping kein konkreter Suchbegriff uebrig ("was tun bei Regen in Graz" -> q leer), laeuft die RPC mit q=NULL rein ueber setting + Location-Radius + Tags, deterministisch sortiert (Tag-Match-Anzahl DESC, dann name ASC) — die Regen-Query darf nie an fehlendem trgm-Term scheitern. visible=true und duplicate_of IS NULL, OHNE Datumsfilter; Ranking: trgm-similarity + Tag-Match-Anzahl.

- **Location-Strategie (deterministisch):** Bundesland-Intent -> Filter auf die kanonische bundesland-Spalte (lowercase-IDs, Task 1); die Bundesland-Whitelist wird dabei VOLLSTAENDIG aus einer SoT gespeist (alle 9 kanonischen IDs zentral definieren — die bestehende Inline-Map BUNDESLAENDER_KEYS in smart-query.ts ist unvollstaendig und wird daraus ersetzt/ergaenzt). Stadt-/Ort-Intent -> Radius-Expansion mit **deterministischem Gemeinde-Extractor als PRIMAEREM Resolver, eigene pure Funktion `detectGemeindeInQuery(rawQuery)` in smart-query.ts**: scannt den ROHEN Query-Text (normalisiert: lowercase, Umlaute, Bindestriche) token-basiert gegen die normalisierten ALL_GEMEINDEN-Namen (src/lib/gemeinden/data.ts, 2.028 Eintraege) — laeuft VOR dem Pfad-Gating und unabhaengig vom LLM (LLM-location ist nur optionaler Hint). **Ambiguitaets-Politik (verbindlich):** Match nur bei (i) Kontextwort davor (in/bei/nahe/um/rund um) ODER (ii) Mehr-Token-Gemeindenamen ODER (iii) eindeutigem Nicht-Woerterbuch-Token; Stoplist fuer kollisionstraechtige Namen (Gemeinden, die mit Alltagswoertern kollidieren) wird gepflegt; im Zweifel KEIN Match (kein stiller Radius-Filter). Negative Tests Pflicht. **Nach einem Match wird der Gemeinde-Ausdruck aus den Suchtermen GESTRIPPT** (analog parseQuery-Location-Stripping bei Events) — sonst ueber-constrained der Ortsname die name-trgm-Suche der RPC ("mountaincart dorfgastein" muss als q="mountaincart" + Radius Dorfgastein laufen) — damit funktionieren auch "Dorfgastein" oder "Lutzmannsburg", nicht nur die kuratierte CITIES-Map; CITIES bleibt als Abkuerzung fuer Mehrfach-Gemeinde-Staedte (Wien/Graz/...). Centroid = Gemeinde-Registry-lat/lng; bbox-Vorfilter ueber btree(lat)/btree(lng) (Task-1-Indizes) + Haversine-Nachfilter, Radius via getCityHub(...)?.radiusKm ?? 15 km. "was tun bei Regen in Graz" = Stadt-Intent + **Filter setting='indoor'** (deterministisches Feld aus Task 1 — nicht freie Tag-Interpretation). fetchCandidates behaelt seinen event-only-Contract; rankCandidates bleibt event-only. SCORE_ORDER/baseQuery (:177-193, EXPLAIN-Kommentar) und filter_after_date>=NOW()-Invariante NICHT anfassen (Memory semantic_search_future_only).
- Response: additives Feld activityMatches; bestehende Consumer brechen nicht (Feld wird ignoriert bis UI-Block da ist).
- **Consumer-Contract (verbindlich):** `count`/`matches` bleiben event-only; hasResults = matches.length > 0 || activityMatches.length > 0. **ALLE Consumer von /api/search/semantic werden in diesem Task auditiert und angepasst** — laut Route-Kommentar mindestens V4EntdeckenSmartMode UND V4ConciergeCard (+ ggf. Concierge-SSE-Pfad); keiner darf eine activity-only-Response (matches=[], count=0, activityMatches>0) als "keine Ergebnisse" rendern.
- UI: Block "Passende Aktivitaeten" in V4EntdeckenSmartMode mit Typ-Badge, Links auf /aktivitaet/*.
